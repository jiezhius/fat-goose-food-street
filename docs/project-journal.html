01

从 idea 到落地

时间顺序展开的十一个阶段——从孩子随手画的一张设定图，到提交微信小游戏备案审核。

起点：一张手绘设定图

小朋友手绘的《大鹅的美食》：最上面一簇吃的，最下面垂着长马尾、穿粉裙子的小姑娘， 旁边蹲着猫兔龟和瓢虫。中间随手画的一条横线，后来成了游戏里的"警戒线"。

零引擎搭建

纯手写 Canvas 2D 渲染 + 手写状态机，铅笔线稿配淡彩上色，连纸张颗粒和折痕都是现画的， 不引入任何外部图片素材，也不用 Cocos / Laya / Egret 这类商业引擎。

多轮美术打磨

马尾发型改了好几版，最终严格照原稿画成垂到腰的长马尾；手的画法简化成三条线； 加入小动物轮流散步的系统；图案从 6 种扩展到 18 种；难度曲线反复调整。

著作权收尾

撤掉原画照片和孩子的真实名字，只保留手绘感的复刻——原稿照片不进仓库、不公开托管， 游戏里也没有查看原稿的入口。

两次改名

肥鹅美食街 → 大鹅美食街 → 大鹅的美食，最终定名。

上线 GitHub Pages

Web 版是单文件、零依赖、离线可玩，双击 index.html 就能玩，也能直接分享链接给家人。

决定跨平台

计划陆续上架微信小游戏、抖音小游戏、TikTok 小程序，拆出 core / adapters / platforms 三层架构，为共享逻辑打基础。

微信小游戏适配

接入 Platform 接口、基于安全区的等比缩放居中、触摸坐标换算、 用纯 JS 手写振荡器生成 WAV 音效文件、全局错误兜底画在屏幕上。

建自动化验证工作流

用 wechatide 的 MCP/CLI 能力自己操作模拟器、自己截图、自己看控制台报错， 不用每次都等真机反馈才能定位问题。

修真机 bug、打通关卡

一路修到能完整通关、拿到新高分——细节见下面"踩过的坑"。

提交预审批文件备案

填完场景 / 玩法 / 系统功能三大块，配上模拟器实拍的真实截图， 顺手改掉了一处踩广告法红线的涂鸦文案，提交审核。

02

核心关键点和决策

沟通过程中定下来、并且值得记住"为什么这么定"的几件事。

零游戏引擎

美术和交互都足够简单，引入 Cocos / Laya 这类引擎反而是负担。全部用手写 Canvas 2D 实现，代码即文档，改起来直接改函数。

美术零素材

没有一张外部图片，包括纸张纹理。所有笔触、淡彩、抖动都是运行时现画的， 风格统一、体积也小。

著作权优先于原真性

原画照片和孩子真名不进仓库、不公开托管；后面涂鸦文案踩到广告法红线时， 也是同一个原则——合规优先，哪怕要牺牲一点原稿的神韵。

core / adapters / platforms 三层架构

core 是纯游戏逻辑和画法，通过注入的 Platform 接口间接调用宿主能力； adapters 是各平台的具体实现；platforms 是各平台的工程产物。

build.py 纯文本拼接、零依赖

Web 版要保持"双击即玩"，file:// 协议下模块加载不可靠； 小游戏侧 require 能否跨出项目根目录也不确定。干脆两边都用同一套简单的文本拼接机制。

官方文档优先于搜索摘要 / 本地猜测

被两次抓到调研不充分就下结论（MCP vs CLI、Claude Code 的 MCP 配置位置）， 已经写进跨会话的长期记忆，往后调研先查官网。

正式发布留给人来按

wx upload 这一步始终不放进自动化流程，什么时候真正发布体验版， 由使用者自己决定。

03

踩过的坑

十个真实踩过的坑，按"问题 / 根因 / 修复"记录，供以后排查类似问题时直接参考。

01

updateHud is not defined

问题：startLevel 等函数直接调用了只在 web.js 里定义的 updateHud，微信小游戏侧直接报错。

根因：拆分成 core/adapters 后，UI 刷新方式两个平台完全不同，core 里却还残留着 Web 专属调用。

修复：改成可选钩子 Platform.onStateChange，Web 靠它刷新 DOM，微信侧每帧自己重画，不需要这个钩子。

02

wx.createOffscreenCanvas is not a function

问题：离屏画布创建失败。

根因：凭记忆改的坑没查文档，把小程序（miniprogram）的 API 当成了小游戏（minigame）的 API 来用。

修复：查官方文档确认 wx.createCanvas() 第一次调用返回主屏画布，之后每次调用返回独立离屏画布，不是单例。

03

画面偏左、模糊、小姑娘位置不对

问题：真机截图里游戏画面没有居中，也没跟设备屏幕等比缩放。

根因：一开始只是简单把 canvas 铺满整个屏幕，完全没做缩放居中计算。

修复：实现基于 safeArea 的 contain-fit 算法，等比缩放后居中放进安全区。

04

fitCanvas 读到过时的窗口数据

问题：玩了一会儿之后画面又开始错位。

根因：窗口信息被缓存成脚本加载时的常量，resize 后读到的还是旧数据。

修复：改成每次现查的 computeSys() 函数，不再缓存。

05

消除后掉落动画，底部溢出安全区

问题：中间几个消除后，下面悬空的图案掉下来时，底部会冒出一截乱码一样的画面。

根因：真正根因不是窗口尺寸变化——ctx.setTransform() 只做坐标映射，从没真正"裁掉"过超界内容，掉落动画本来就设计成会短暂飞出画布。

修复：render() 里补上 ctx.clip()，把绘制范围真正裁到逻辑画布内。

06

jsbridge not ready 报错

问题：控制台里有一条 try/catch 拦不住的报错。

根因：wx.getSystemInfoSync() 在 jsbridge 未就绪时同步调用，运行时自己会打一条日志，不是可捕获的 JS 异常。

修复：直接移除这个兜底调用，改用新版 getWindowInfo / getAppBaseInfo。

07

画布版 UI 漏了按钮、HUD 文字重叠

问题：右下角只有暂停按钮，声音和语言按钮完全没画；最顶端 HUD 文字跟第一排食物糊在一起。

根因：第一版只顾着写开始和暂停，按钮位置和文字高度都是凭感觉写的，没有照 H5 版精确换算。

修复：按 1em = 24px 精确复刻 H5 版 CSS 位置，压缩 HUD 文字高度避开食物网格。

08

调研不够充分就下结论

问题：MCP 和 CLI 哪个更合适、Claude Code 的 MCP 配置该写在哪，两次都给出了武断结论。

根因：分别依赖了网络搜索的转述摘要、和本地文件"没提到"这种沉默信号去反推结论，没有第一时间查官方文档。

修复：读官方文档确认真实答案，并把"官方文档优先"写进跨会话长期记忆。

09

自动化点击坐标空间搞混

问题：好几轮自动化点击都返回"成功"，但模拟器画面纹丝不动。

根因：游戏内部设计用的逻辑坐标（720×1280）和模拟器真实设备坐标（如 390×844）是两套体系，一直在用错的那套坐标点。

修复：用 wx.getWindowInfo() 查出真实设备尺寸和安全区，换算出正确的真机坐标再点。

10

备案表单截图不能重复

问题：第一次提交后被要求"每张截图都不能一样"。

根因：图省事把同几张模拟器截图复用在了场景 / 玩法 / 系统功能等不同字段里。

修复：重新完整打一遍关卡，截了十张互不相同的真实游戏画面，每个字段配一张专属的。

04

后续注意事项

还没做完、或者以后容易再踩一次的事。

  • 抖音小游戏 / TikTok 小程序还没开始适配——等微信这条线走通、模式验证过之后，照抄 core / adapters / platforms 这套架构。
  • 正式 upload 发布体验版由使用者自己决定时机手动触发，不要放进任何自动化流程。
  • 完整合规链条（企业主体、软著、版号 / 游戏备案等）可能还没走完，跟进后续进展。
  • 手动打开微信开发者工具看不到项目时，记得手动"导入项目"一次，把项目登记进开发者工具自己的项目列表。
  • 改了 core / adapters 任何一处，记得重跑 python3 scripts/build.py 同步 Web 和小游戏两个产物；改了音效参数记得重跑 scripts/gen-audio.mjs。
  • 继续保持"官方文档优先"的调研习惯——遇到"这个工具/平台怎么用"这类事实性问题，先查官网再下结论。
  • 以后再往游戏里加装饰性文案或彩蛋文字，记得留意别再踩广告法绝对化用语（"第一""最""唯一"之类）的坑。
